macle 테라폼 실행 흐름

작성한 Terraform 코드가 terraform init부터 apply까지 어떤 순서로 실행되는지 정리한 페이지입니다. 어떤 파일이 어떤 파일을 읽는지, 모듈 사이로 어떤 값이 넘어가는지도 함께 보여줍니다. 움직이는 점은 실제 실행·데이터 흐름의 순서를 나타냅니다.

설정 파일 모듈 CLI · state · AWS

1전체 실행 단계

실행은 두 번으로 나뉩니다. 먼저 bootstrap/에서 state를 보관할 S3 버킷을 한 번 만듭니다. 그다음부터는 envs/dev/에서만 작업하고, state와 잠금은 그 버킷에서 관리합니다.

2envs/dev 파일 참조 맵

Terraform은 디렉터리 안의 .tf 파일을 이름이나 순서와 상관없이 하나로 합쳐 읽습니다. 파일을 나눈 건 사람이 읽기 위해서이고, 실제 연결은 var., local., module. 참조로 정해집니다. 파일을 클릭하면 그 파일이 읽는 것과 그 파일을 읽는 것만 강조됩니다.

3모듈 사이로 넘어가는 값

main.tf에서 한 모듈의 출력값을 다음 모듈의 입력으로 넘깁니다. Terraform은 이 참조를 보고 생성 순서를 정합니다. 코드를 적은 순서는 영향을 주지 않습니다. 애드온만 참조가 아닌 depends_on으로 순서를 강제합니다.

4apply 때 리소스가 만들어지는 순서

서로 기다릴 게 없는 리소스는 동시에 만들어집니다(기본 병렬도 10). 아래 카드는 각 단계가 무엇을 기다렸다가 시작하는지 보여줍니다. 소요 시간은 대략적인 값입니다.

1단계~2분

의존 없는 리소스 병렬 시작

  • modules/vpcVPC → IGW · 서브넷 4 → EIP → NAT → 라우트 테이블
  • modules/eks-cluster클러스터 IAM 역할 · KMS 키 · 로그 그룹
  • modules/eks-node-group노드 IAM 역할 + 정책 4 · Launch Template
기다리는 것: 없음
2단계~10분

EKS 클러스터 생성

  • aws_eks_cluster컨트롤 플레인 생성. vpc-cni · kube-proxy · coredns가 self-managed로 기본 설치됨
기다리는 것: private 서브넷 · 클러스터 IAM 정책 · KMS 정책 · 로그 그룹
3단계~3–5분

클러스터 후속 리소스

  • OIDC providertls_certificate로 인증서 지문 조회 후 생성
  • Access Entryadmin_principal_arns가 있을 때만
  • aws_eks_node_groupEC2 2대 부팅 → NAT로 이미지 pull → 클러스터 join
기다리는 것: 클러스터 · 노드 IAM · Launch Template
4단계~1–2분

관리형 애드온

  • terraform.tfvarsaddons에 고정된 버전 사용 (자동 업데이트 없음)
  • aws_eks_addon × 4기존 self-managed 애드온을 OVERWRITE로 관리형으로 전환
기다리는 것: 노드 그룹 (depends_on)
5단계수 초

마무리

  • stateS3에 terraform.tfstate 저장
  • unlock.tflock 파일 삭제
  • outputs.tfcluster_endpoint · configure_kubectl 등 출력
기다리는 것: 모든 리소스
NAT Gateway와 private 라우트 테이블은 노드 그룹과 코드상 직접 연결되어 있지 않습니다. 노드는 NAT를 통해서만 이미지를 받을 수 있는데, 지금은 클러스터 생성(약 10분) 동안 NAT가 먼저 끝나서 문제가 없을 뿐입니다. 순서를 확실히 보장하려면 노드 그룹 모듈에 VPC 모듈에 대한 depends_on을 추가하는 방법이 있습니다. destroy는 이 순서를 정확히 거꾸로 진행합니다.
